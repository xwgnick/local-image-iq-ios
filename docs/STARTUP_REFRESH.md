# 启动图库检查精简 · 0.5.1（build 14）

## 原来在做什么

每次冷启动、从后台返回或收到图库变化通知时，AppState 都执行 refresh。它不是重新算 embedding，也不请求照片原图或下载 iCloud 照片，但旧路径会：

1. 枚举已授权图片的 ID／修改时间，核对删除、修改与权限变化。
2. 在 SQLite 中清除失效记录及无引用的地点向量。
3. 首次读取并解析离线地点包（约 15 MB，进程内复用）。
4. 加载分词器、主图像模型和文本模型，验证运行时接口。
5. 为了统计可搜索照片数，读取、JSON 解码并验证整库 768 维向量。

整个流程都显示“正在检查图库”，并阻止实际搜索。没有真机分阶段计时，不能断言以上某一步占用多少秒。额外 19 个图像模型只在索引的缓存 miss 时懒加载，不是启动创建 20 个模型。

## 本轮改动

- refresh 改用 `PhotoEncoding.inspectResources()`：检查必要资源位置、小 manifest 与接口声明，不加载 Core ML 模型或解析分词器大文件。
- 首页计数改为 SQLite 元数据聚合；不读取 embedding 列，也不为了显示数量解码整个索引。
- 孤立地点清理改为先求精确 `(text, model_version)` 差集再删除，避免旧无索引相关查询重复扫描照片表；不更改表结构、模型版本或缓存策略。
- 搜索、索引及单照片诊断仍执行完整模型准备和向量校验，不允许损坏向量进入排名。资源存在不等于运行时已经加载；首次真实操作可能承担延迟后的加载，失败仍按失败报告，不冒充无结果。
- 已授权照片枚举、撤权／删除／修改处理、取消回滚和原任务串行排空机制不变。

## 明确没有做的事

**不是彻底跳过检查，也不是保证秒开。** 完整授权快照、SQLite 元数据核对、首次地点包解析仍有成本；保留“正在检查图库”提示，不用改文案掩盖等待。尚未缓存全库内存向量或迁移 JSON 为二进制，不新增计时器、任意容量限制、后台任务或自动恢复分支。

统计是“当前授权与缓存身份下的已保存行数”，不是每次启动的向量健康扫描：损坏 embedding 可被计数，但实际搜索仍拒绝它。未授权、旧模型／预览策略、旧 geography 不会被混入当前对应计数；地点引用缺失不算已保存地点。

20 worker、HQ224／Fast、文本／图像模型、地点权重、结果数量、翻译、缓存版本和数据库 schema 均不变。已有有效索引直接沿用，不卸载、不清索引、不重新准备照片。

## 验证状态

实现与新增测试已写入，待原生完整验证后交付；当前可安装版仍为 0.5.0 / build 13。

- 资源检查测试：有效 metadata 配合故意损坏的 runtime 文件仍可检查、完整准备则拒绝；资源缺失、manifest 错误、tokenizer 异目录和取消。
- SQLite 测试：版本／geography／共享地点计数、损坏引用、计数不读取坏向量、取消、无过期照片时仍清理覆盖产生的孤立地点、跨模型与 Unicode 精确键。
- 实际 worker refresh 测试：分别记录 inspection／完整准备／预测调用；重复刷新不完整准备；搜索仍准备与拒绝坏向量；撤权／删除／修订与失败枚举等不退化。

这组测试证明执行路径改变，不代表 iPhone 速度测量。最终仍需在用户实际图库上确认启动等待是否明显缩短。
