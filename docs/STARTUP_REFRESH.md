## 原来在做什么

每次冷启动、从后台返回或收到图库变化通知时，AppState 都执行 refresh。它不是重新算 embedding，也不请求照片原图或下载 iCloud 照片，但旧路径会：

1. 枚举已授权图片的 ID／修改时间，核对删除、修改与权限变化。
2. 在 SQLite 中清除失效记录及无引用的地点向量。
3. 首次读取并解析离线地点包（约 15 MB，进程内复用）。
4. 加载分词器、主图像模型和文本模型，验证运行时接口。
5. 为了统计可搜索照片数，读取、JSON 解码并验证整库 768 维向量。

整个流程都显示“正在检查图库”，并阻止实际搜索。没有真机分阶段计时，不能断言以上某一步占用多少秒。额外 19 个图像模型只在索引的缓存 miss 时懒加载，不是启动创建 20 个模型。

## 本轮改动

- refresh 改用 `PhotoEncoding.inspectResources()`：检查必要资源位置、小 manifest 与接口声明，不加载 Core ML 模型或解析分词器大文件。
- 首页计数改为真正的 SQLite 元数据聚合，分别按当前模型／预览策略及 geography 身份统计；不读取 embedding 列，也不为了显示数量 JSON 解码整个索引。
- 孤立地点清理改为先求精确 `(text, model_version)` 的 `EXCEPT` 差集，再用 `IN` 删除，避免旧相关子查询重复扫描照片表；不更改表结构、模型版本或缓存策略。
- 搜索、索引及单照片诊断仍执行完整模型准备和向量校验，不允许损坏向量进入排名。**首次搜索的模型／分词器加载是延后，不是取消**；搜索仍读取向量，失败仍按失败报告，不冒充无结果。
- 完整已授权照片快照与失效记录清理、撤权／删除／修改处理、取消回滚和原任务串行排空机制不变；搜索前后的授权复查保留。首次约 **15 MB** 地点边界包解析及进程内 parser／resolver 复用仍保留。

## 明确没有做的事

**不是彻底跳过检查，也不是保证秒开。** 完整授权快照、SQLite 元数据核对、首次地点包解析仍有成本；保留“正在检查图库”提示，不用改文案掩盖等待。尚未缓存全库内存向量或迁移 JSON 为二进制，不新增计时器、任意容量限制、后台任务或自动恢复分支。

统计是“当前授权与缓存身份下的已保存行数”，不是每次启动的向量健康扫描：损坏 embedding 可被计数并使界面显示就绪，但实际搜索仍按原校验抛错。未授权、旧模型／预览策略、旧 geography 不会被混入当前对应计数；地点引用缺失不算已保存地点。

UI、AppState、Photos 代码没有改动；20 worker／并发、HQ224／Fast、文本／图像模型权重、排名、地点权重、结果数量、翻译、缓存版本和数据库 schema 均不变。未改变计时器或后台机制。

**使用原 Sideloadly Apple 账号／原有效 Bundle ID 覆盖安装**。已有 build 10+ 当前策略有效图像／地点索引及就绪语言包直接沿用，**不卸载、不清索引、不重建，也不必 Index / resume**。看到“正在检查图库”不意味着要重做索引；正常搜索／看图即可。安装入口见 [WINDOWS_IPHONE_INSTALL.md](WINDOWS_IPHONE_INSTALL.md)。
