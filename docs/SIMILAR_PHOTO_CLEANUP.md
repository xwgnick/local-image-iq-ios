## 1. 入口与操作

功能是把相似照片按组展示，按照片数量排序，支持多选、独立对比和明确确认后的系统删除；沿用简约黑金界面。

1. 首页搜索框下方点「**相似照片清理**」，与「筛选」相邻；不是调试入口，也不是单张照片的「找相似」。
2. 打开页面**不会自动扫描**。点「开始分组」才读取现有索引；之后可手动「重新分组」。
3. 默认余弦阈值 **0.96**，可在 **0.90–0.99** 间按 **0.01** 调整，越高越严格。
4. 修改阈值会取消旧分组并清除旧结果、选择和待确认删除，**不会自动重新分组**。
5. 结果按组内照片数量从多到少排列，显示张数和最低相似度；可逐张勾选、全选本组或清空选择。
6. 每组有独立「**对比本组照片**」按钮。对比时仅勾选待删除，返回清理页后统一点删除并确认。

开始分组需要前台、照片可读权限、模型就绪、图片索引统计已知且非零，以及没有其他忙碌任务。
未就绪时提示先授权或手动更新图片索引；不代替用户授权、更新索引或开启 iCloud 下载。
实现：[../App/UI/ContentView.swift](../App/UI/ContentView.swift)、[../App/UI/SimilarPhotoCleanupSheet.swift](../App/UI/SimilarPhotoCleanupSheet.swift)。

## 2. 相似度与分组含义

- 复用当前 SigLIP 2 的 **768 维图片向量**，计算图片之间的余弦相似度；不结合 OCR、查询翻译或地点加权。
- **0.96 不是 96% 的重复概率，也不是 96% 像素一致。**这是语义相似建议，不是逐像素重复检测。
- 高分仍可能是不同主体、不同事件或不能互相替代的照片；没有实测准确率、误删率或最佳阈值保证。
- 每个显示组至少两张；新成员必须与**已有每一名成员**的相似度均不低于阈值，不加放宽容差。
- 因此 A≈B、B≈C、但 A 与 C 不达标时，不会仅靠连通链把三张合成一组；只与组首相似也不够。
- 「最低相似度」是**组内所有照片对的实际最小余弦值**，不是平均值或只对组首的分数。
- 输入先按照片 ID 稳定排序；依次取未分配照片为种子，候选按与种子的相似度降序尝试，同分按 ID。
- 候选通过全成员检查才加入；已分配照片不再进入别组。最终组按数量降序、同数量按组 ID 稳定排序。
- 这是**确定性的贪心、不重叠分组**，不是穷举全部极大团或寻找最大团；不保证找出每一对相似照片。
- 单张未成组项目不显示，但计入处理进度；种子和显示顺序**不是推荐保留或质量排名**。

实现：[../App/Photos/SimilarPhotoGrouping.swift](../App/Photos/SimilarPhotoGrouping.swift)。

## 3. 哪些照片参与

- 范围是系统当前允许访问的图片资产，包括有限授权范围；不局限于搜索结果、已显示分页或当前搜索筛选。
- 沿用现有枚举：`includeHiddenAssets = true`、`includeAllBurstAssets = true`。**可访问的隐藏照片可能包含在内**，连拍也不自动排除；不是自动扩大系统授权。
- 没有新增按日期、相册、截图、Live Photo 或隐藏状态自动排除的策略。
- 必须存在**当前模型及图片输入策略**的索引记录，并与当前完整 `PhotoRevision` 一致：ID、修改时间、创建时间（含 `nil`）。
- 先读取 revision 元数据并筛选，再解码向量；修改时间或创建时间变化的记录都跳过，不拿旧图向量作清理建议。
- 「参与分组」是有效候选数，含未成组单张；「已变化」是当前可访问、当前策略记录中 revision 过期的数量。
- 「未索引」包含没有记录及只有旧模型／旧策略记录的照片；失去访问权的照片不参与这些当前范围计数。
- 新增、已变化、旧模型或未索引照片不会自动补算。先手动更新图片索引，再手动重新分组。
- 当前候选向量若维度、有限性或单位范数不合法，会报错；不悄悄修向量、重建索引或隐藏错误。

与普通搜索仍可沿用旧图片向量不同，清理建议要求完整 revision 当前有效。
范围实现：[../App/Photos/PhotoLibraryClient.swift](../App/Photos/PhotoLibraryClient.swift)、[../App/Persistence/SQLitePhotoStore.swift](../App/Persistence/SQLitePhotoStore.swift)。

## 4. 只读、失效与取消

- 一次成功分组有 **3 次完整授权图片快照**：初始、计算前、计算后；后两次必须与初始 ID／完整 revision 一致。
- 同时检查授权状态及 PhotoKit 变化代数；生产通知先增加代数，再通知界面，计算边界也会验证。
- 返回结果携带验证闭包：发布前同步验证全部返回成员；勾选、全选及删除确认阶段再核验相关选中成员的 revision 和访问状态。
- `AppState.photoLibraryEpoch` 在图库变化、手动更新图片索引、全部重建及清除索引时失效；首页和清理页据此清掉旧分组与选择。
- 系统照片中的编辑／删除、有限授权调整等变化同样使旧结果失效；不会保留旧确认继续操作，也不会自动重新分组。
- 分组可手动取消；进入后台或真正关闭清理页会取消读任务。返回前台只恢复可操作状态，不自动续跑。
- 被取消的旧读任务会等待真正结束后再开始后续显式请求；旧进度、晚到结果不能覆盖新会话。
- 分组服务仅检查模型资源元数据并只读索引，**不加载模型做推理、不请求照片像素、不执行 OCR、不写图片／文字索引、不清理数据库**。
- 以上“不请求像素”仅指分组计算；显示组内缩略图和打开对比仍会按现有许可读取预览。

## 5. 计算成本

设有效候选数为 $N$、向量维度 $D=768$：最坏相似度计算为 $O(N^2D)$，逐种子候选排序另有最坏 $O(N^2\log N)$ 比较成本。
计算阶段额外构造**一份 $N\times768$ 连续矩阵**，并使用 $O(N)$ 分数、范数与分配状态等临时空间；**不构造 $N\times N$ 相似度矩阵**。
这不表示总内存只有一份向量：已解码记录和结果还会驻留；大图库的耗时、峰值内存和发热未在真机验证。
没有新增照片数／组大小上限、日期窗口、整批超时、自动缩量或后台调度；由用户显式启动，在前台运行并可取消。
进度按实际处理候选计数，含已分配组员和未成组单张；不是剩余秒数或线性耗时承诺。

## 6. 两张并排对比

- 对比页使用真正的两栏并排视图，竖屏和大字模式也保持左右两栏；从本组分别选择两张，选到另一侧照片时交换，避免两侧相同。
- 初始展示完整照片、按比例适配（`.aspectFit`），不是清理列表的裁剪网格；没有自动选最佳照片或默认保留者。
- **只为当前两张请求像素**，不为整组预取大图；请求目标依据各栏点数、屏幕倍率和照片比例计算，不请求原始文件。
- 像素顺序：本地显示 HQ → 不足时本地短边 HQ224 → 仍不足且用户已明确允许联网时的显示 HQ；所有阶段保持完整照片。
- 只有尝试过的 HQ 都没有可读像素，才回退本地 Fast224；已有小 HQ 不会被 Fast 替代。普通错误、权限错误和取消不被回退隐藏。
- HQ、返回尺寸或 `degraded=false` 均不是清晰度保证。保留返回栅格、方向和比例，不通过像素插值冒充更多真实细节。
- 原生双指缩放为 **1–4 倍显示缩放**，双击还原；缩放不会请求新一档更高分辨率，也不会恢复缺失细节。
- 切换照片、尺寸、网络许可或访问身份时取消／替换旧请求；前后核验组成员、两张 revision、授权及变化代数，失效后清除像素。
- 「勾选删除」只改变共享选择，**不准备或提交删除**；需点「返回」，再在清理页使用明确的删除按钮。

## 7. 删除的是系统照片

**这是从系统 Photos 图库删除资产，不是仅从本地索引移除。**删除 Live Photo 时操作的是整个资产，不只是当前静态预览。
启用 iCloud 照片的设备可能把删除同步到 iCloud 和其他设备，**即使 App 的预览网络开关关闭也一样**；该开关不控制系统图库同步。
Photos 通常将照片移入「最近删除」，但保留时间和恢复能力由系统决定；不保证永久可恢复或固定恢复期限，App 也不能撤销原文件删除。

删除链路如下：

1. 初始没有任何自动勾选或默认保留照片；用户逐张或全选本组后，底栏显示实际选中数量。
2. 点「删除 N 张」捕获当前会话、完整有序 revision 列表及将被全部选中的组数，显示应用确认提示。
3. **允许选中某组全部照片**；确认中明确提示有多少组不会保留照片，不设置强制留一张的限制。
4. 取消确认不删除；选择、阈值、会话或访问状态变化使旧确认无效。确认时再次检查捕获值与当前选择完全一致。
5. 删除服务仅按捕获 ID 获取资产，校验**整个选择**的授权、存在性、图片类型、完整 revision 和 `canPerform(.delete)`，任一不满足则不提交删除请求。
6. 提交 `performChanges` 前预检一次；进入系统排队的 changes 闭包后重新获取并验证全部资产，最后紧邻提交再检查授权／变化代数。
7. 只在**一个 Photos 事务中发出一次批量 `deleteAssets`**；不逐张提交、不扩展选择、不用新查询替换原确认。系统还可能显示自己的确认。

最终检查不能锁住系统图库，不能承诺 Photos 与应用状态绝对原子一致。
排队中、实际修改开始前取消可阻止请求；**修改开始后的取消不是回滚**，必须等系统真实完成回调，不以取消覆盖成功，也不自动重试。
状态层用独立删除任务等待服务结果；后台、页面读状态失效不会取消它，控制器 `deinit` 也只取消读任务，不取消已交出的删除任务。
删除期间禁用选择、分组及关闭操作；系统确认造成的临时 inactive 不当作进入后台。错误用通用中文，不透出照片 ID、路径或系统私密描述。
实现：[../App/Photos/PhotoDeletionService.swift](../App/Photos/PhotoDeletionService.swift)、[../App/State/SimilarPhotoCleanupState.swift](../App/State/SimilarPhotoCleanupState.swift)。

## 8. 删除后与隐私边界

- 服务返回成功、失败或取消后，仍在的控制器都会清除旧分组、选择和确认；报告实际结果，**必须手动重新分组**。
- 清理功能不自动更新／重建图片索引，也不自动清理数据库。图片索引统计可能保留旧计数，直到手动更新；不展示精确释放磁盘空间的承诺。
- 已删除或失去访问权的 ID 会由搜索的当前访问过滤排除，不要求先物理删除数据库旧行才能阻止检索。
- 旧 OCR 正文可能仍留在本机，直到用户手动更新文字索引时清理，或明确清除索引；关闭 OCR、删除系统照片或撤权都不是立即擦除正文的保证。
- 这沿用 [PHOTO_TEXT_SEARCH.md](PHOTO_TEXT_SEARCH.md) 的隐私边界；普通图片索引更新不等于文字库清理。
- [权限用途说明](../App/Info.plist) 已明确“仅在勾选并确认后删除系统照片”，并提示可能同步；不能继续对新版作全局“不删除照片”承诺。
- “不自动删除、不修改原图像素、不向应用服务器上传照片”与明确确认后的系统删除不矛盾；旧版文档中的不删除描述按其历史版本理解。
- 「清除索引」仍只清本地索引，和此处的系统照片删除是两个不同操作；不要为升级清库或卸载。
